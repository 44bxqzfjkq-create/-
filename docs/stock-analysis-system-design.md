# 株式分析システム 設計書

> 本書は「設計書」です。この段階では実装コードは含みません。
> 目的は、既存の分析方針を壊さずに、**投資候補を発見し、分析材料を整理し、人間が最終判断できる状態にする**システムを設計することです。
> 実際の投資判断（発注・自動売買）は本システムの対象外とします。

- 対象市場: **日本株（東証）中心**
- データ予算: **無料ソースを基盤に、有料API併用可**
- 出力形式: **Markdown / HTML / CSV**（本書 §11 で使い分けを規定）
- 作成日: 2026-08-09
- ステータス: ドラフト v0.1（レビュー・承認待ち。承認までコード実装は行いません）

---

## 0. 設計原則（システム全体を貫く前提）

1. **判断は自動化しない。材料整理までを自動化する。**
   スコアやランキングは「注目度」であって「買い推奨」ではない。最終判断は人間。
2. **「業績が良い」で終わらせない。**
   業績・成長性・バリュエーション・市場期待・株価・リスクを**総合**し、さらに**過去データで手法自体を検証**できることを最優先要件とする。
3. **データの出所を必ず記録する（Provenance ファースト）。**
   すべてのデータ点に「出典 / 取得日時 / 対象期間 / 取得パラメータ / APIバージョン」を付与する（§4.4）。
4. **Point-in-Time（PIT）を守る。**
   バックテストでは「その時点で実際に入手可能だった情報」だけを使う。開示日・発表日を厳密に扱い、**先読み（look-ahead）バイアス**と**生存者バイアス（survivorship）**を排除する（§9）。
5. **再現性。**
   同じ入力・同じルール設定・同じ基準日なら、同じレポートが再生成できる（設定はすべてファイル化）。
6. **既存11分析方針の保存。**
   既存ルール（業績/決算/財務/バリュエーション/成長性/株価/市場期待/投資仮説/反証/リスク/複数投資家視点）を分析エンジンの11モジュールとして1対1で実装する（§2, §6）。

## 1. 株式分析システムの全体像

### 1.1 コンセプト
「スクリーニングで候補を絞り → 個別に多面的分析 → 手法の妥当性を過去データで検証 → 監視リスト化して継続追跡 → 人間が読めるレポートに集約」という**一連のパイプライン**。

### 1.2 レイヤー構成

```
┌──────────────────────────────────────────────────────────────┐
│  L5  レポーティング層   Markdown / HTML / CSV 出力            │
├──────────────────────────────────────────────────────────────┤
│  L4  アプリケーション層  スクリーニング/決算分析/企業比較/    │
│                          バックテスト/監視追跡                 │
├──────────────────────────────────────────────────────────────┤
│  L3  分析エンジン層      既存11分析方針を11モジュール化       │
│                          + 総合スコアリング                    │
├──────────────────────────────────────────────────────────────┤
│  L2  処理・指標計算層    正規化 / 財務指標 / PIT整合           │
├──────────────────────────────────────────────────────────────┤
│  L1  データ取得層        J-Quants / EDINET / 株価 / 期待値     │
│                          + Provenance(出典記録)               │
├──────────────────────────────────────────────────────────────┤
│  L0  ストレージ層        raw / processed / cache / metadata    │
└──────────────────────────────────────────────────────────────┘
```

### 1.3 データフロー（1サイクル）

```
[ユニバース定義] → [データ取得(出典記録付き)] → [正規化・指標計算]
      → [分析エンジン11モジュール] → [総合スコア] 
      → [スクリーニング] → [個別深掘り(決算/比較)] 
      → [バックテストで手法検証] → [監視リスト更新] → [レポート出力]
```

## 2. 分析エンジン：既存11方針のモジュール化

既存の分析方針を**そのまま**11モジュールにマッピングする。各モジュールは「入力データ → 指標 → 所見（根拠つき）→ サブスコア」を返す。総合スコアは各サブスコアの重み付き合成（重みは `config/analysis_weights.yaml` で外部化）。

| # | 既存方針 | モジュール | 主な指標・出力 |
|---|---------|-----------|--------------|
| 1 | 企業の業績分析 | `performance` | 売上/営業利益/当期利益の水準・推移、利益率、セグメント別 |
| 2 | 決算分析 | `earnings` | 直近決算の実績、会社計画比、進捗率、上方/下方修正、サプライズ |
| 3 | 財務分析 | `financials` | 自己資本比率、ROE/ROA/ROIC、有利子負債、CF、運転資本、Altman Z等 |
| 4 | バリュエーション分析 | `valuation` | PER/PBR/PSR/EV/EBITDA/配当利回り、DCF簡易、過去レンジ内での位置 |
| 5 | 成長性分析 | `growth` | 売上/利益CAGR、成長の質(増収増益/一過性)、再投資効率 |
| 6 | 株価分析 | `price_action` | トレンド、移動平均、ボラティリティ、相対力(対TOPIX/業種)、出来高 |
| 7 | 市場期待との比較 | `market_expectation` | コンセンサス vs 実績/会社計画、期待の織り込み度合い |
| 8 | 投資仮説の作成 | `hypothesis` | 「なぜ上がりうるか」の仮説を構造化(ドライバー/前提/検証条件) |
| 9 | 反証分析 | `counter_analysis` | 仮説を崩す条件、ベア視点、確証バイアス点検 |
| 10 | リスク分析 | `risk` | 業績/財務/流動性/集中/規制/為替/イベントリスク、下方シナリオ |
| 11 | 複数投資家視点からの評価 | `investor_views` | バリュー投資家/グロース投資家/配当投資家/クオンツ等の視点別評価 |

> **重要**: 8(仮説)・9(反証)・11(複数視点)は、数値だけでなく**構造化された文章所見**を出す。ここが「業績が良い企業リスト」との決定的な差。総合スコアには「反証が強い＝スコア減点」というペナルティ機構を入れる。

### 2.1 総合スコアの考え方
- 各モジュールが 0–100 のサブスコア + 「根拠」+「信頼度(データ充足度)」を返す。
- 総合 = Σ(サブスコア × 重み)。ただし **反証(counter)** と **リスク(risk)** は減点方向に効く。
- データ欠損時はスコアを出さず「判定保留」を明示（欠損を0点扱いしない）。
- スコアは**順位付けの補助**であり、レポートには必ず「根拠」と「反証」を併記して人間が覆せるようにする。

## 3. 必要なデータの整理

### 3.1 データカテゴリ

| カテゴリ | 具体項目 | 用途モジュール |
|---------|---------|--------------|
| 銘柄マスタ | コード、名称、業種(33/17)、市場区分、上場/廃止日、発行済株式数 | 全般・ユニバース |
| 株価 | 日次OHLCV、調整後終値、売買代金 | price_action, valuation |
| 財務(PL) | 売上高、営業/経常/当期利益、EPS、セグメント | performance, growth |
| 財務(BS) | 総資産、自己資本、有利子負債、現預金 | financials |
| 財務(CF) | 営業/投資/財務CF、FCF | financials |
| 決算開示 | 決算短信、実績、**会社計画(ガイダンス)**、修正、**開示日時** | earnings |
| 決算スケジュール | 決算発表予定日 | watchlist, PIT |
| 市場期待 | アナリストコンセンサス(売上/利益/目標株価) | market_expectation |
| 指数・ベンチマーク | TOPIX、業種別指数、東証REIT等 | price_action, backtest |
| 需給・その他 | 投資部門別売買、空売り比率、信用残 | risk, price_action |
| マクロ(任意) | 金利、為替(USD/JPY)、コモディティ | risk |

### 3.2 データ粒度・保持期間
- 株価: 日次、**最低10年**（バックテストのため。長いほど良い）
- 財務: 四半期・通期、**最低10年**
- コンセンサス: 取得できた時点からの**スナップショット履歴**（後から遡れないため、取得日ごとに保存が必須）
- 銘柄マスタ: **廃止銘柄を含む**時系列（生存者バイアス回避に必須。§9）

### 3.3 「対象期間」の二重管理
財務データは2つの日付を必ず持つ：
- **会計期間**（例: FY2025 Q1 = 2025/4–6）
- **開示日 / 入手可能日**（例: 2025/8/1 に短信開示）
→ バックテストは後者で「その時点で使えたか」を判定する。

## 4. データ取得方法の整理

### 4.1 主要データソース（日本株）

| ソース | 種別 | 取得内容 | 費用 | 位置づけ |
|-------|------|---------|------|---------|
| **J-Quants API**(JPX公式) | REST | 株価、財務諸表、決算発表予定、銘柄マスタ(廃止含む)、投資部門別、空売り、指数 | 無料枠あり/有料で期間拡張・遅延短縮 | **中核データ源** |
| **EDINET API**(金融庁) | REST/XBRL | 有価証券報告書・四半期報告書(詳細財務、注記、セグメント) | 無料 | 詳細財務の一次情報 |
| **TDnet**(適時開示) | 開示 | 決算短信、会社計画、修正 | 無料(APIは限定的) | 会社計画・速報。J-Quants/EDINETで補完 |
| **yfinance** 等 | 非公式 | 株価・簡易財務(`XXXX.T`) | 無料 | 補助・クロスチェック用。品質は保証されない |
| **有料コンセンサス** (IFIS/QUICK/株探系 等) | 商用 | アナリストコンセンサス、目標株価 | 有料 | §7分析(市場期待)の要。無料入手は困難(§12) |
| 為替・マクロ | 各種 | USD/JPY、金利 | 無料〜 | リスク分析補助 |

> **推奨構成**: `J-Quants(有料ライトプラン) + EDINET(無料)` を基盤にし、市場期待だけは入手可否・費用を見て段階導入。まず無料枠で骨組みを作り、必要に応じ有料化。

### 4.2 取得方式
- **バッチ取得**（日次/週次）: 株価・マスタ・決算スケジュール。
- **イベント駆動**: 決算発表日に合わせて当該銘柄の決算データを取得（§9 監視追跡と連動）。
- **オンデマンド**: 個別深掘り時に不足データを取得。
- **キャッシュ**: 取得済みは `data/cache/` に保存し、APIレート制限を回避。再取得は差分のみ。

### 4.3 レート制限・障害対策
- リトライ（指数バックオフ）、レート制御、失敗ログ。
- APIキーは環境変数 / `.env`（リポジトリにコミットしない）。`config/` にはキー**参照名**のみ。

### 4.4 出典記録（Provenance）— 必須設計
すべての取得データに以下のメタデータを付与し、`data/metadata/` に保存＋データ本体にも埋め込む。

```yaml
# 例: 1回の取得に対するメタデータレコード
record_id: "jq_fins_7203_20250801"
source: "J-Quants /fins/statements"
source_type: "official_api"
api_version: "v1"
endpoint_params: { code: "7203", ... }
fetched_at_utc: "2026-08-09T02:15:00Z"
fetched_at_jst: "2026-08-09T11:15:00+09:00"
target_entity: "7203 トヨタ自動車"
accounting_period: "FY2026 Q1 (2025-04-01..2025-06-30)"
disclosure_date: "2025-08-01"          # 入手可能になった日(PIT用)
data_hash: "sha256:..."                 # 改変検知・再現性
retrieved_by: "ingestion/jquants_client v0.1"
```

- レポートには**必ずデータ出典と取得日時を脚注**として出す（§11）。
- これにより「いつ時点の、どこ由来のデータで、どの期間を分析したか」が常に追跡可能。

## 6. 銘柄スクリーニング機能 仕様

### 6.1 目的
広いユニバースから、11分析方針で深掘りする価値のある**候補**を機械的に絞る。**足切りであって推奨ではない**。

### 6.2 入力
- ユニバース（例: プライム全銘柄 / 特定業種 / 時価総額◯以上）
- 条件セット（`screening_rules.yaml`）。ANDだけでなく「加点式」も可。

### 6.3 条件カテゴリ（例）
- **バリュエーション**: PER < X、PBR < Y、配当利回り > Z、過去レンジ下位◯%
- **成長性**: 売上CAGR > X%、営業利益CAGR > Y%、増収増益連続◯期
- **財務健全性**: 自己資本比率 > X%、有利子負債/EBITDA < Y、FCF > 0
- **収益性**: ROE > X%、ROIC > WACC(簡易)
- **株価/需給**: 対TOPIX相対力 > 0、出来高下限、ボラ上限
- **市場期待**: コンセンサス上方修正、実績 > コンセンサス
- **除外条件**: 上場◯年未満、流動性不足、直近下方修正、債務超過

### 6.4 出力
- 条件通過リスト（CSV + Markdown表）
- 各銘柄に「どの条件を満たし/落ちたか」内訳（透明性）
- 総合スコア（§2.1）による順位（あくまで参考順位）
- **プリセット**: 「割安×成長」「高配当×健全」「相対力×業績上方」等を `screening_rules.yaml` に定義

### 6.5 設計上の注意
- 条件は**すべて設定ファイル化**（コード変更なしで調整可能）。
- スクリーニング条件自体を§9でバックテスト検証できるようにする（＝スクリーニングとバックテストは同じルール定義を共有）。

## 7. 決算分析機能 仕様

### 7.1 目的
個別銘柄の直近決算を、実績・会社計画・市場期待の3軸で評価し、「決算の中身」を構造化する。

### 7.2 分析項目
- **実績評価**: 売上/各利益の前年同期比、QoQ、利益率変化
- **会社計画比**: 通期計画に対する進捗率（季節性補正の注記つき）、達成確度
- **修正**: 上方/下方修正の有無・幅・理由
- **サプライズ**: 実績 vs コンセンサス（入手できる場合）
- **質の評価**: 増益の中身（本業か一過性か、為替影響、特益/特損）
- **セグメント**: 伸びている/縮んでいる事業（EDINET注記活用）
- **ガイダンスの解釈**: 会社トーン、保守/強気の傾向（過去の達成実績と対比）

### 7.3 出力
- 決算サマリー（Markdown、1銘柄1ページ）
- 実績/計画/期待の対比表
- 「ポジティブ材料 / ネガティブ材料 / 要監視点」の3分類
- §8(仮説)・§9(反証)モジュールへの連携（決算が仮説を支持/否定するか）

### 7.4 イベント連携
- 決算発表予定日（§4.1）を監視し、発表後に自動で当該銘柄の決算分析を走らせ、監視リスト（§10）に差分を反映。

## 8. 企業比較機能 仕様

### 8.1 目的
複数銘柄（同業他社/候補群）を同一基準で横並び比較し、相対的な魅力・割高割安を可視化する。

### 8.2 比較軸
- 規模: 時価総額、売上、利益
- 成長性: 売上/利益CAGR
- 収益性: 利益率、ROE/ROIC
- 財務: 自己資本比率、負債、FCF
- バリュエーション: PER/PBR/PSR/EV/EBITDA/配当利回り
- 株価: 年初来/対TOPIX相対力
- 市場期待: コンセンサス、目標株価乖離
- 総合スコア（§2.1）と11モジュール別サブスコア

### 8.3 比較の作法
- **業種・会計基準の違いを明示**（例: 銀行と製造業のPBRは比較不可）。
- 単純な優劣でなく「どの投資家視点(§11)ではどれが優位か」を併記。
- 偏差値化/パーセンタイル化で相対位置を表現。

### 8.4 出力
- 比較表（CSV + Markdown）
- レーダーチャート/バーチャート（HTMLダッシュボード）
- 「相対的に割安かつ成長」「割高だが質が高い」等の分類コメント

## 9. バックテスト機能 仕様（最重要）

> 本システムの核心。「業績が良い企業を並べる」ではなく、**採用した分析・スクリーニング手法が過去に有効だったかを検証**する。

### 9.1 目的
- スクリーニング条件・スコアリング（§2, §6）を過去の任意時点に適用したら、その後どうなったかを測る。
- 手法の**有効性・安定性・弱点**を定量化し、人間がルールを改善できるようにする。

### 9.2 検証の枠組み
- **リバランス方式**: 基準日ごと（月次/四半期）にルールを適用 → 上位N銘柄でポートフォリオ構成 → 次リバランスまでのリターンを記録。
- **ベンチマーク**: TOPIX（配当込み）や業種指数と比較。
- **指標**:
  - リターン系: 累積/年率リターン、超過リターン(vs TOPIX)、勝率
  - リスク系: 最大ドローダウン、ボラティリティ、シャープ/ソルティノ
  - 手法妥当性: **IC(情報係数)**（スコアと将来リターンの順位相関）、分位ポートフォリオ(Q1〜Q5)のリターン単調性、ヒットレシオ
  - 頑健性: 期間分割(前半/後半)、業種別、地合い別(上昇/下落局面)での安定性

### 9.3 バイアス排除（設計の生命線）
- **先読み(look-ahead)防止**: 財務は§3.3の「開示日」を使い、基準日時点で未開示のデータは使わない。株価も基準日終値まで。
- **生存者バイアス防止**: ユニバースに**廃止銘柄を含む**（J-Quastsの廃止情報を利用、§3.2）。上場していた当時の構成銘柄で判定。
- **リスタテメント注意**: 後日修正された財務でなく、当時発表された値（as-reported）を優先。
- **取引コスト/流動性**: 売買代金下限、スリッページ・手数料を控除可能に。
- **オーバーフィッティング防止**: 検証期間と学習期間を分ける（walk-forward）。過度なパラメータ最適化を戒める注記をレポートに出す。

### 9.4 入力・設定（`backtest_config.yaml`）
- 期間、リバランス頻度、ユニバース、採用ルールID、保有銘柄数、コスト、ベンチマーク。

### 9.5 出力
- パフォーマンスサマリー（表 + 資産曲線チャート）
- 分位別リターン、IC推移、ドローダウン曲線
- 「この手法はどの局面で効き、どこで効かないか」の所見
- **限界の明示**: PIT精度、コンセンサス履歴の欠損、廃止銘柄カバレッジ等（データ品質がバックテスト信頼度に直結するため必ず記載）

## 10. 監視銘柄の継続追跡の仕組み 仕様

### 10.1 目的
候補・保有・ウォッチ銘柄を継続的にフォローし、「変化」を検知して人間に通知する。

### 10.2 監視リスト管理
- `config` または `data/` に監視リスト（コード、追加理由、追加時点のスコア/仮説）を保持。
- 各銘柄に「投資仮説(§8)」と「その検証条件・反証条件(§9)」を紐付け。

### 10.3 検知イベント
- **決算**: 発表予定日到来 → 決算分析(§7)自動実行 → 仮説の支持/否定を判定
- **業績修正**: 上方/下方修正の開示
- **スコア変化**: 総合スコア/サブスコアが閾値以上変動
- **バリュエーション**: PER/PBR等が設定レンジを逸脱
- **株価**: 相対力の急変、新高値/新安値、ボラ急騰
- **リスク**: 空売り比率急増、信用残変化 等

### 10.4 運用（実行トリガ）
- 日次/週次バッチ（cron 相当）。
- Claude Code on the web の **Trigger/Routine**（スケジュール実行）や SessionStart hook を活用し、定期取得→差分検知→レポート生成を回す設計を想定（§12で実現性を整理）。

### 10.5 出力
- 監視ダッシュボード（HTML）: 銘柄別の現状スコア・仮説状態・直近イベント
- **変化アラート**（Markdown/差分）: 「何が」「いつ」「どれだけ」変わったか＋出典
- 仮説トラッキング: 仮説が「進行中/支持/否定/要見直し」のどの状態か

## 11. 最終レポートの出力設計

### 11.1 出力形式の使い分け

| 形式 | 用途 | 特徴 |
|------|------|------|
| **Markdown** | 個別分析レポート、決算サマリー、変化アラート | Git差分で履歴追跡でき、レビューしやすい。**一次成果物** |
| **HTML** | スクリーニング/比較/監視ダッシュボード | チャート・インタラクティブ表。閲覧性重視。既存index.html資産を活用可 |
| **CSV** | スクリーニング結果、比較表、バックテスト時系列 | 二次利用・表計算・再分析向け |

### 11.2 レポート種類
1. **個別銘柄レポート**（Markdown/HTML）: 11モジュール全出力 + 総合スコア + 仮説 + 反証 + リスク + 複数投資家視点。**必ず「結論の前に反証」を載せる**。
2. **スクリーニングレポート**（CSV/Markdown/HTML）: 通過銘柄、条件内訳、順位。
3. **企業比較レポート**（CSV/HTML）: 横並び表＋チャート。
4. **決算レポート**（Markdown）: §7の内容。
5. **バックテストレポート**（HTML/CSV）: §9の内容。手法の有効性と限界。
6. **監視/変化レポート**（HTML/Markdown）: §10の内容。

### 11.3 全レポート共通の必須要素（Provenance反映）
- **データ出典一覧**（ソース名・エンドポイント・APIバージョン）
- **取得日時**（UTC/JST）と**対象期間**（会計期間・株価as-of）
- **データ充足度/欠損の明示**（判定保留項目を隠さない）
- **免責**: 「本レポートは分析材料であり投資助言・売買推奨ではない。最終判断は利用者が行う」
- **再現情報**: 使用したルール設定ファイルのバージョン/ハッシュ

### 11.4 レポート構造テンプレ（個別銘柄・例）
```
# {銘柄} 分析レポート ({基準日})
## 0. サマリー(総合スコア/一言所見)  ※スコアは参考。以下の根拠で覆せる
## 1. 業績   ## 2. 決算   ## 3. 財務   ## 4. バリュエーション
## 5. 成長性 ## 6. 株価   ## 7. 市場期待との比較
## 8. 投資仮説（強気シナリオ）
## 9. 反証分析（弱気シナリオ・仮説が崩れる条件）   ← 意図的に強調
## 10. リスク   ## 11. 複数投資家視点(バリュー/グロース/配当/クオンツ)
## 付録: データ出典・取得日時・対象期間・欠損項目・免責
```

## 12. 実現性の整理（本書で最も重要な結論の一つ）

### 12.1 現在の環境で実現可能なこと
- **アーキテクチャ全体の構築**（Python + ファイルベース設定 + Git管理）。
- **無料データでの骨組み**: J-Quants(無料枠)・EDINET(無料)・yfinanceによる株価/財務取得と正規化。
- **11分析モジュール**の実装（数値指標 + 構造化所見）。
- **スクリーニング / 企業比較 / 個別分析 / 決算分析**の実装。
- **出典記録(Provenance)**、対象期間・取得日時の記録。設計原則(§0)は完全に実現可能。
- **Markdown / CSV レポート**、および静的**HTMLダッシュボード**。
- **バックテストの枠組み**（PIT・生存者バイアス対策込み。ただしデータカバレッジに依存＝下記）。
- **定期実行**: Claude Code on the web の Trigger/Routine やローカル cron でのバッチ運用（§10）。

### 12.2 追加で必要なもの
- **APIキー/契約**:
  - J-Quants アカウント（無料登録。過去期間拡張・遅延短縮は**有料プラン**推奨）。
  - EDINET は登録のみで無料。
  - **市場期待(アナリストコンセンサス)** は無料入手が困難 → 有料データ（IFIS/QUICK系や商用API）契約が必要。未契約時は§7の「市場期待」を限定機能として明示。
- **Python実行環境と依存ライブラリ**（pandas 等。requirements 定義は実装時）。
- **秘密情報管理**: `.env`／シークレット（キーはコミットしない）。
- **ストレージ**: 10年分データ保持のディスク（本セッションのコンテナは揮発性のため、永続化方針＝Gitに入れるデータ/入れないデータの線引きが必要）。
- **（任意）チャート描画**の依存（HTMLダッシュボードのグラフ）。

### 12.3 技術的に難しい / 注意が必要なこと
1. **アナリストコンセンサス(市場期待)の取得**: 日本株では公的な無料ソースが乏しく、**時系列スナップショットの蓄積**（後から遡れない）が必要。有料契約かつ日々の保存運用が前提。§7の質はここに強く依存。
2. **Point-in-Time財務の厳密性**: 開示日の正確な扱い、後日修正(リスタテメント)の分離。J-Quants/EDINETの提供仕様に依存し、完全なas-reported再現は難所。
3. **生存者バイアス対策の完全性**: 廃止銘柄の当時株価・財務のカバレッジが限定的な場合、バックテスト精度に上限が出る。カバレッジをレポートで開示する設計で対処。
4. **決算短信の会社計画(ガイダンス)・非財務情報の構造化**: TDnet短信やXBRLからの抽出は様式差・注記の非定型性で難易度が高い。段階的に精度向上させる。
5. **データ品質のクロスチェック**: 無料ソース(yfinance等)は誤差・欠損あり。複数ソース突合の仕組みが必要。
6. **コンテナ揮発性による永続化**: 大量データを本環境に置き続けられない。外部ストレージ or 取得の再現性(キャッシュ+Provenance)で対応。
7. **やらないこと（意図的な非対象）**: 自動発注・自動売買・投資助言の提供。ティック/板・超短期売買。これらは本システムの目的外。

### 12.4 実現性サマリー表

| 機能 | 無料のみ | 有料併用 | 難易度 |
|------|:---:|:---:|:---:|
| データ取得基盤+出典記録 | ◎ | ◎ | 低 |
| 11分析モジュール | ○ | ◎ | 中 |
| スクリーニング | ◎ | ◎ | 低 |
| 決算分析 | △(計画/期待が弱い) | ◎ | 中 |
| 企業比較 | ◎ | ◎ | 低 |
| 市場期待との比較 | ✕〜△ | ○ | **高** |
| バックテスト(PIT/生存者対策) | △(カバレッジ依存) | ○ | **高** |
| 監視・継続追跡 | ○ | ◎ | 中 |
| レポート(md/html/csv) | ◎ | ◎ | 低 |

◎=十分 / ○=概ね可 / △=制約あり / ✕=困難
